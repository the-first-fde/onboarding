## 업무 규칙 후보와 질문

- **R1 시작 시점**: 지원자 DB `현황`이 「채용」으로 바뀌고 입사자 DB 행이 생긴 뒤(매핑 2절). 계획 생성 자체는 사람이 요청한다. 외부 ATS에는 입사 확정 데이터가 없고 별도 노션 오퍼 페이지도 없으므로(매핑 1절), 이 둘을 입력으로 쓰지 않는다.
- **R2 조건 판정**: `[경력]` = 경력 구분이 경력, `[노트북 지급]` = 노트북 지급 여부 체크. 아니면 「해당 없음」(양식 3절). 처음 보는 조건 태그는 판정하지 않고 질문.
- **R3 기한 계산**: `D±N`은 입사일 기준, `확정+N일`은 확정일 기준, 주말이면 앞 평일(양식 3절). 공휴일도 앞 평일로 당기는 것은 PROVISIONAL(Q23). `첫 주`·`3주 차`·`첫 정기 사무실 출근일`의 날짜 환산은 양식에 정의가 없다(Q23).
- **R4 기한 경과**: 계산한 기한이 기준일보다 이르면 기한은 두고 `기한 경과`로 표시한다(확정~입사 14일 미만일 때).
- **R5 실행 구분** (위에서부터 처음 맞는 것): `DECISION` 평가·전환 결정 → `HR_ONLY` 담당이 인사이고 개인정보·외부 발송·서명·입사자 계정 확인이 걸림 → `REQUEST` 담당이 리더·총무·버디·입사자 → `AGENT` 담당이 인사이고 개인정보 없이 노션 페이지 생성·캘린더 등록으로 끝남. `HR_ONLY` 안의 개인정보 없는 일정 등록은 `에이전트 보조`로 따로 표시. 양식 v3.2에 적용하면 `AGENT`는 2건뿐이다(ON-14, ON-47).
- **R6 확인 질문**: 필수 입력 빈칸, 버디·노트북 빈칸, ON-03 비고(총무 절차 변경 여부), 기한 경과, 최근 30일 안 양식 변경, 미정의 조건, 계약직·인턴의 수습 항목.
- **R7 인수인계 — 보류**: 경력 입사이거나 대체 채용이면 질문만 남긴다. 퇴사자 정보·인수인계 문서는 읽지 않고 링크는 사람이 연결한다(Q24).
- 오류·재시도·중복: 같은 입사자 코드로 다시 만들면 새 초안을 만든다(기존 진행 상태는 건드리지 않음). 멱등성·저장은 Q07.
- 시간대: Asia/Seoul. 날짜만 다룬다.
- 외부 시스템과 최소 권한: 노션 읽기만(입사자 DB, 인사팀 문서 DB 온보딩 행, 사무실 출근 일정 DB). 쓰기 없음. 현재는 mock(Q06).
- 보존/삭제/마스킹/로그: 금지 값은 받지 않는다. 로그에는 입사자 코드·항목ID·상태만 남긴다.
- 다른 담당자와 충돌/공통화: 입사자 DB 필드·체크리스트 항목은 안내·준비와 공통(Q14). 실행 구분과 넘김 목록 형식은 검토·승인(Q25)과 안내·준비 입력에 맞춰야 한다.
- 샘플 요청: 공휴일 목록 출처, `첫 주`·`3주 차` 날짜 정의(Q23).

## 인수 조건 후보 (가상 fixture 작성 전 근거)

- 데이터팩 체크리스트 예시 1절의 입력을 넣으면, 예시 2절 「지금 열려 있는 항목」의 기한과 같은 날짜가 나온다. 주말 보정 사례(D+89가 일요일)를 포함한다.
- 같은 입력에서 경력 구분을 신입, 노트북 지급을 아니오로 바꾸면 ON-07 · ON-11 · ON-15 · ON-21이 「해당 없음」이 된다.
- 출력 어디에도 이름·이메일·연락처·처우가 없다.
- 위 기대값은 데이터팩 원문이 아니라 검토된 가상 fixture로 옮겨 테스트한다.

## 개인정보 보호 방법 (1 · 2 공통)

보안 가이드 2부 6절은 개인정보를 다루는 경우 보호 방법을 설계에 적도록 요구한다. 두 에이전트는 개인정보를 처리하지 않도록 설계했고, 읽힐 수 있는 경로마다 아래처럼 막는다.

| 개인정보가 있을 수 있는 곳 | 막는 방법 | 근거 |
|---|---|---|
| 입사자 DB 이름 · 개인 이메일 · 연락처 · 특이 사항 | 허용 칸 목록만 사용. 읽혀도 출력·로그에 옮기지 않고 입사자 코드로만 부른다 | 가이드 2부 2·3절 |
| 체크리스트 「처리한 사람」 · 비고 | 사람은 역할로만, 비고는 업무 요지만 옮긴다. 개인 사정은 뺀다 | 가이드 2부 3절 |
| 수습 취합 시트 이름 · 점수 · 종합 판단 · 결과 | 날짜·회신 칸만 사용 (Q28) | 가이드 2부 2절 |
| 합류 정보 · 서류 제출 DB, 계정 · 장비 요청 DB, 서류 폴더 | 읽지 않는다 (제목이 사람 이름이거나 원본 서류) | 가이드 1부 1번 |
| 실명 ↔ 코드 대조표 | AI 도구에 넣지 않는다. 노션 안에서 권한자만 본다 | 가이드 2부 3절 |
| 처우 · 연봉 · 면접 점수 · 레퍼런스 원문 | 입력으로 받지 않는다 | 매핑 3절, 가이드 2부 2절 |

- 쓰기와 배포: 두 에이전트는 MCP 쓰기를 하지 않고 외부 웹 배포도 없다. 배포가 필요해지면 가이드 2부 6절에 따라 직속 상사 승인과 1부 2번 점검을 먼저 거친다.
- 로그: 입사자 코드 · 항목ID · 상태 · 날짜만 남긴다.
- 테스트: 데이터팩 원문이 아니라 검토된 가상 fixture를 쓴다.
- 숫자 기준: 회의에서 들은 수치나 도구 이름이 아니라 데이터팩 수치를 쓴다(데이터팩 안내, 기준표 1절).

### 업무 규칙 후보와 질문

- **P1 합치기**: 두 체크 위치(준비 체크리스트 · 입사자별 온보딩 페이지)를 항목ID로 합친다. 같은 항목이 두 곳에 있으면 체크된 쪽을 따른다.
- **P2 상태 판정** (위에서부터 처음 맞는 것, 양식 3절 값 기준):
  - 완료 계열 — 체크됨: 완료일 ≤ 기한이면 `완료`, 기한 뒤면 `늦게 완료`, 다시 확인한 날이 있으면 `다시 확인 후 완료`
  - `해당 없음` — 계획에서 해당 없음
  - `다시 확인 필요` — 체크가 비었는데 같은 담당의 더 뒤 단계 항목이 체크됨, 또는 비고에 처리했다는 기록이 있음 (예시 3절 사례 유형)
  - `이슈` — 이슈 신호에 표시, 또는 비고에 회신 대기·문제 발생·다시 요청 기록 (Q26)
  - `지연` — 체크 안 됨, 기한 < 기준일
  - `신규` — 체크 안 됨, 기준일 − 항목 생성일 ≤ 2일. 항목 생성일 = `added_date` 또는 계획 `created_date` (Q27 확정: 생성 후 2일)
  - `진행 중` — 체크 안 됨, 신규 기간이 지났고 기한 전
  - 표시 `기한 임박` — 신규·진행 중 중 기한 ≤ 기준일+2일. 판정 상태와 별개
  - 데이터팩 양식 3절의 「진행 중」(시작했고 기한 전)·「예정」과 뜻이 다르다. 팀 정의를 쓰고 보고에 차이를 알린다
- **P3 제외**: 완료 계열과 해당 없음은 열린 항목에서 빼고 건수만 낸다.
- **P4 단계 보고(기준 도달)**: ① 한 단계(양식 4절 묶음)의 해당 항목이 모두 완료 계열이 되었을 때, 또는 ② 기준 시점(D-7 · D-1 · D+0 · 첫 주 끝 · D+29 · D+59 · D+89)에 도달했을 때 보고를 만든다. 보고에는 남은 항목, 다음 단계에서 시작할 항목, **후속 조치 제안**, **작성 항목**(완료일 · 처리한 사람 · 다시 확인한 날이 빈 완료 항목)을 넣는다.
- **P5 후속 조치 제안**: 판정 상태별로 정한다. 지연 → 담당 역할 확인 요청 또는 리마인드 초안 요청(발송은 사람, Q16) / 다시 확인 필요 → 누구에게 무엇을 확인할지 / 이슈 → 비고 요지와 결정이 필요한 사람 / 신규 → 담당 역할에게 알렸는지 확인 / 기한 임박 → 오늘 챙길 일.
- **P6 쓰기 없음**: 상태 칸·체크를 바꾸지 않는다. 상태 변경 주체는 사람(검토·승인 담당과 경계 합의 — Q25).
- 시간대·로그·보존: 1과 같다.

### 인수 조건 후보

- 데이터팩 체크리스트 예시의 기준 시점 기록을 넣으면, 예시 2절 「지금 열려 있는 항목」과 같은 항목이 열린 항목으로 나오고 완료 항목은 빠진다.
- 예시 3절 유형(체크가 비었지만 처리된 항목)이 `다시 확인 필요`로 잡힌다.
- 출력에 이름·점수·평가 판단이 없다. 검증은 가상 fixture로 한다.
