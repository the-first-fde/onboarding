# 담당자별 잠정 데이터 요구사항: 산출물 검토·HITL·승인 상태 관리

- 담당자/업무: 검토·승인 담당 / 업무 분할 「4. 사람의 검토 및 승인 (HITL)」
- 상태: PROVISIONAL (인터페이스 공유용) / 팀 합의 항목은 NEEDS_CLARIFICATION
- 관련 Issue/Spec/ADR: Issue 미등록(등록 승인 대기) / [Spec](../specs/review-approval.md) / ADR 없음
- 확인된 근거(출처·날짜·확인자): 고객사 데이터팩 20261125(가명·가공 자료), 2026-11-25 검토·승인 담당 확인. 경로·절 번호로만 인용한다. 사람은 데이터팩 표기대로 역할(인사 담당자, 경영지원 담당, 리더, 버디)로만 쓴다.
  - `02_온보딩/06_입사_안내메일.md` 머리말: 메일은 인사 담당자가 초안 작성·직접 확인 후 발송, 자동 발송 없음
  - `02_온보딩/06_입사_안내메일.md` 메일 1~6·챗: 메일별 받는 사람·참조·시점·체크리스트 ID
  - `02_온보딩/08_첫주_캘린더_요청문구.md` 1절(캘린더 제목·참석자), 3-1~3-4절(계정·장비·팀 권한 요청 양식)
  - `02_온보딩/02_온보딩_체크리스트_양식.md` v3.2 (ON-01~56), `04_온보딩_체크리스트_변경기록.md`
  - `00_공통/02_조직도.md` 3절(온보딩·수습 업무 담당), `00_공통/05_AI_사용_보안_가이드.md`
- 샘플 수령 여부: 데이터팩 수령(로컬 전용, Git 미포함). 비식별 가상 fixture는 아직 만들지 않음.
- 확인된 사실:
  - 발송 전 검토·승인은 인사 담당자가 한다. 메일 3 참조 리더, 메일 6 참조 버디는 수신 참조일 뿐 검토자가 아니다 (`06_입사_안내메일.md` 머리말·메일 3·메일 6, 2026-11-25 안내·준비 담당 확인).
  - 경영지원 담당은 요청 발신 전 승인자가 아니라, 요청을 받은 뒤 검토·처리하는 수신자다 (`08_첫주_캘린더_요청문구.md` 3-2·3-3절, 2026-11-25 안내·준비 담당 확인).
  - 수습 평가와 정규 전환 결정은 소속 본부장이 한다 (`00_공통/02_조직도.md` 3절). 자동화 대상이 아니다.
  - 실제 메일 발송과 입사 확정은 사람이 수동으로 한다 (루트 CLAUDE.md).
  - 업무 분할 8번(온보딩 계획 검토·검증 Review Agent)은 구현하지 않는다 (2026-11-25 검토·승인 담당 결정).
- 잠정 가정(확정 정책으로 사용 금지):
  - A1. 검토 단위는 산출물 1건 = 검토 항목 1건. 온보딩 계획은 입사자 1명당 1건.
  - A2. 승인 만료는 없다. 대신 내용 해시가 바뀌면 재승인이 필요하다.
  - A3. 반려는 별도 상태 없이 「수정필요」로 처리한다.
  - A4. 「보류」 해제는 인사 담당자가 한다.
  - A5. HITL은 원본 양식과 초안의 차이 요약만 붙이고, 규칙 위반 판단은 하지 않는다.

## 업무 규칙 후보와 질문

- 규칙 후보/근거/확인자/미확정 시 영향:
  - 상태 전이(PROVISIONAL): 초안생성→검토대기(차이 요약 후 자동) / 검토대기→승인완료·수정필요·보류 / 수정필요→검토대기(재생성 후) / 보류→검토대기(이슈 해결 후) / 승인완료→검토대기(내용 해시 변경 시 재승인) / 승인완료+`executed_at`→대기열 제거. 그 밖의 전이는 오류로 거부한다.
  - 승인자는 모든 발송 전 산출물에서 인사 담당자다. 미확정 시 영향: 역할별 승인 권한 검사가 단순해짐.
  - 계정 요청(3-3) 검토 때 「신청 권한이 직무에 맞고 넘치지 않는지」를 검토 요청 문구에 넣는다.
- 오류·재시도·중복·시간대·승인·수동 전환:
  - 같은 `item_id`·같은 해시 재등록은 기존 항목을 돌려준다(중복 생성 없음).
  - 시각은 KST, 날짜 `2026-11-23`·시간 `14:00` 형식(`00_공통/01_기준표.md`).
  - 승인 대기 중 자동 재시도·자동 승인은 없다.
- 외부 시스템과 최소 권한(현재 MCP 쓰기 금지): HITL은 외부 시스템을 직접 호출하지 않는다. 다른 담당자의 MCP mock 쓰기 앞에 `require_approved`를 둔다.
- 보존/삭제/마스킹/로그 정책: `ReviewItem`과 `history`에 이름·연락처·주소·처우·주민번호·인증정보를 넣지 않는다(`00_공통/05_AI_사용_보안_가이드.md`). 로그에는 `item_id`·상태·해시만 남긴다. 보존 기간은 NEEDS_CLARIFICATION.
- 다른 담당자와 충돌/공통화가 필요한 사항:
  - 안내·준비 담당: `artifact_type` 목록, `content` 형식, 승인 지점별 `request_review` 호출 위치, 외부 쓰기 mock 앞 게이트 적용.
  - 계획·진행 담당: 온보딩 계획 검토 단위, `executed_at` 전달 방식(진행현황은 「진행 중」으로 받음), 반송된 요청을 새 수정 요청으로 받는 형식.
  - HITL 상태와 섞지 않을 상태: 체크리스트 상태, 계정·장비 진행현황, 서류 처리상태(`01_노션DB_구조.md`). 계획·진행 담당 업무 분할 자료의 「신규·진행 중·완료·지연·이슈」는 데이터팩 표기와 달라 확인 필요.
  - 팀: 공통 State 위치, checkpointer, `hire_ref` 식별자 규칙, MCP mock 소유자.
- 샘플 요청(가상·비식별만, 실제 자료는 Git 금지): 가상 입사자 1명의 메일 초안 1건과 수정 요청 1건을 테스트 안에서 직접 만든다. `fixtures/` 공통 업무 데이터는 만들지 않는다.

## 계약 확정 절차

샘플/근거 수령 → 담당자 검증 → 3인 충돌 조정 → 공통 계약·버전·호환성 합의 → 사람 승인.
그 전에는 확정 Schema/State/공통 업무 테스트 데이터로 사용하지 않는다.
