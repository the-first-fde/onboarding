# 코드와 업무 결과를 리뷰하기

**학습 목표**는 개발 경험에 관계없이 요구사항·산출물·검증을 대조하고, 고칠 위치와 영향을 설명하는 것이다. 담당 Spec·잠정 계약과 [공통 리뷰 양식](../../.github/templates/review.md)을 준비한다. 리뷰는 서로 다른 시각에서 실제 문제를 찾는 절차다. Diff는 두 상태 사이의 변경이며, 터미널에서 앞에 `-`가 붙은 줄은 이전 내용, `+`는 새 내용을 보여준다.

## 실습 · 안내 초안의 발송 경계 검토

1. **업무 리뷰**에서는 종은의 [안내 Spec](../specs/communication-preparation.md)을 읽고 산출물이 검토 가능한 초안인지 본다. “초안 작성” 단계가 실제 발송을 하는 코드나 문구로 바뀌었다면, 기술 지식 없이도 범위 차이를 지적할 수 있다.
2. **기술 리뷰**에서는 입력과 반환, 예외, 파일·네트워크 쓰기, 실패 테스트를 확인한다. 아래 명령으로 로컬 변경을 확인하고 원격 PR에서는 **Files changed**와 현재 커밋을 함께 본다. 미추적 파일은 일반 diff에 나오지 않는다.

```bash
git status --short --branch
git diff --stat
git diff --staged
```

루트에서 `--stat`으로 영향 파일, `--staged`로 커밋 후보를 확인한다. 읽기 전용이다. 예상과 다르면 status에서 파일 상태와 기준 브랜치를 비교한다. 빈 diff는 변경 없는 근거로 쓰기 전에 미추적 여부를 확인한다.

3. **독립 AI 리뷰**는 구현 결론을 물려받지 않은 별도 세션에서 Spec과 변경을 읽게 한다. code-reviewer와 python-reviewer, 권한 관련 변경이면 security-reviewer 관점을 더한다. 후보 지적을 사람이 파일·실패 조건·실제 테스트와 대조한다.
4. **판정**은 위치, 발생 조건, 영향, 수정 요청으로 적는다. 아래는 예시다.

```text
영역: 안내 초안의 발송 경계
조건: 테스트 입력으로 초안을 생성하는 경로
관찰: 생성 함수가 외부 발송까지 요청한다고 가정
영향: 수동 발송 범위를 위반할 수 있음
결론: 해당 변경이면 Request Changes, 재검토 시 가상 호출만 확인
```

Request Changes는 수정 후 재검토를 요구한다. Approve는 현재 버전에 대한 승인이다. 수정 뒤에는 바뀐 영향과 CI를 다시 확인하고 재승인한다. 일반 1명, 공유 State·권한·승인·보안·MCP 등 고위험은 2명 사람 리뷰가 권장된다. 독립 AI·CI·사람 리뷰의 결과를 구분하고 병합 전 [체크리스트](review-checklist.md)를 확인한다. 승인된 squash merge를 권장하며 문제가 있으면 복구 PR을 연다.

“LGTM”만 남기는 것보다 필요한 근거와 재현을 짚는 의견이 좋다. 리뷰가 차단되거나 담당 범위 밖 문제라면 영향부터 보고하고 Issue를 제안한다. 실제 보안 값은 리뷰에 포함하지 않는다.

**Claude Code 연습** — “별도 세션에서 루트와 대상 README·CLAUDE.md, Spec을 읽고 diff와 테스트를 직접 확인해줘. 재현 가능한 문제만 보고하고 팀 판단 사항은 Issue 초안을 제안해줘.” 사람이 지적이 실제 코드에 맞는지, 시험한 동작인지, 인수 조건을 증명하는지 확인한다.

- [ ] 업무 예시로 실제 자료 없이 한 건의 리뷰 의견을 작성한다.
- [ ] 체크 결과, 미검증 사항, 현재 버전의 승인 상태를 구분한다.
