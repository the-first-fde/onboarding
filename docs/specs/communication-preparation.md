# 담당 업무 Spec: 입사 안내 메일·리더/담당자별 준비 체크리스트 및 요청

- 담당: 종은 (이전 대화 기록, 현재 분담 재확인 필요)
- 상태: DRAFT — 2026-11-25 데이터팩 전체 검토 반영. 업무 구현 보류
- 관련 잠정 데이터 요구: [계약 초안](../contracts/communication-preparation.md)
- 제외: 실제 메일 발송/실제 MCP 쓰기/실제 고객사 데이터/확정 공통 Schema·State·업무 규칙·공통 fixtures
- 현재 검증: NOT RUN (업무 계약 미확정)

이 문서는 데이터팩(로컬 전용)을 경로와 절 번호로만 인용한다. 인물은 역할명으로 쓴다.

### 하지 않는 것
- 실제 발송과 실제 노션·캘린더 쓰기. 발송은 항상 사람이 직접 한다(`06_입사_안내메일.md` 머리말, [ADR 0003](../adr/0003-approval-policy.md)).
- 체크리스트 인스턴스 생성과 진행 상태 관리. [계획·진행 Spec](onboarding-planning.md)이 맡는다(경계는 Q14).
- 승인 상태 저장과 차단 장치 구현. [검토·승인 Spec](review-approval.md)이 맡는다.
- 수습 안내 메일 M1~M13(`03_수습평가/09_안내메일_템플릿.md`)은 담당이 정해지지 않았다(Q15).

## 2. 입력 (PROVISIONAL)
- 입사자 DB 한 행: 속성 목록은 `02_온보딩/01_노션DB_구조.md` 0절, 채용에서 넘어오는 칸은 `01_채용/11_입사확정_노션오퍼_매핑.md` 3절을 따른다.
- 체크리스트 양식 v3.2 항목(ON-01~ON-56): 담당, 기준일, 완료 기준
- 리더가 정리한 합류 배경(ON-34): 챗 소개 문구에 쓴다.
- 비어 있을 수 있는 칸: 버디, 노트북 지급 여부, 사무실 출근 요일, 업무 메일 계정은 사람이 나중에 정한다(매핑 3절). 입력이 비어 있으면 초안을 만들지 않고 보류 사유를 남긴다.

## 3. 산출물

### 3-1 메일과 챗
| 번호 | 메일 | 시점 | 받는 사람 / 참조 | 체크리스트 |
|---|---|---|---|---|
| 1 | 합류 환영과 정보·서류 제출 요청 | D-14 | 입사자 개인 메일 | ON-05 |
| 2 | 온보딩 준비 설문 요청 | D-7 | 입사자 개인 메일 | ON-09 참고 |
| 3 | 첫 출근 안내 | D-7 | 입사자 개인 메일 / 참조 리더 | ON-10 |
| 4 | 첫날 리마인드 | D-1 | 입사자 개인 메일 | ON-19 |
| 5 | 회사 메일 계정 안내 | D+0 | 입사자 개인 메일 | ON-22 |
| 6 | 첫 주 업무 가이드 | 첫 주 | 입사자 회사 메일 / 참조 버디 | ON-46 · ON-47 |
| 챗 | 전사 스페이스 새 구성원 소개 | D+0 | 전사 스페이스 | ON-35 (ON-34 내용 사용) |

- 바꾸는 칸은 메일마다 정해져 있다. 예: 메일 1은 입사일·장소·제출 기한(입사 7일 전)·경력 서류 줄·이력서 줄(`06_입사_안내메일.md` 메일 1 끝).
- 메일 5의 초기 비밀번호, 받는 사람 주소, 연락처는 초안에 넣지 않는다. 자리표시자만 두고 사람이 발송할 때 채운다(`00_공통/05_AI_사용_보안_가이드.md` 2부 2절).

| 담당 | 항목 수 | 항목 ID |
|---|---|---|
| 리더 | 11 | ON-01 · 04 · 09 · 13 · 18 · 24 · 33 · 34 · 37 · 49 · 54 |
| 총무(경영지원) | 6 | ON-11 · 12 · 15 · 16 · 21 · 41 |

- 조건 항목(`[경력]`, `[노트북 지급]`)은 입사자 정보에 맞춰 넣거나 「해당 없음」으로 둔다(양식 3절).
- 기준일(D-14 등)은 입사일로 계산한다. 주말에 걸리면 앞 평일로 당긴다(양식 3절).
- 체크는 각 담당이 하고, 다른 사람이 처리한 항목은 인사 담당자가 확인한 뒤 체크한다(양식 1절).

### 3-3 요청과 일정
| 요청 | 보내는 때 | 받는 사람 / 참조 | 기록 위치 | 체크리스트 |

| 팀 권한 요청 | D-3 | 리더·버디가 있는 스페이스 | 스레드 답으로 초대 담당을 받아 체크리스트에 적음 | ON-24 |
| 캘린더 일정 초안 | 첫 주 일정 확정 전 | 인사 담당자가 만드는 종류만: 공통 안내, 서류 서명, 계정·장비 세팅, AI 교육 | 제목 규칙은 `08_첫주_캘린더_요청문구.md` 1절 | ON-20~30 · ON-47 |

- 팀별 OJT, 리더 1:1, 버디 체크인 일정은 리더나 버디가 만든다(같은 파일 1절). 초안을 만들지 않고 3-2 리더·버디 체크리스트에서 챙긴다.
- 요청 DB의 `진행현황`과 `신청 계정`은 경영지원 담당이 채운다(`01_노션DB_구조.md` 2절).

## 4. 승인 지점 (PROVISIONAL)
모든 지점은 HITL 모듈의 `request_review()`와 실행 차단 장치를 호출한다. 흐름마다 승인 로직을 따로 두지 않는다.

| 지점 | 순서 | 승인자 | HITL에서 처리할 것 |
|---|---|---|---|
| 3-1 메일 | 초안 → (ON-34가 들어간 챗 소개만 리더 확인) → 인사 담당자 승인 | 인사 담당자 | 역할 순서대로 승인해 승인완료. 발송은 항상 사람이 직접 |
| 3-1 ii | 승인 후 Gmail 연동 (더미) | — | 승인완료 상태이고 승인 때 본 내용과 해시가 같을 때만 더미 발송 통과 |
| 3-2 체크리스트 | Notion MCP 페이지 생성 (mock) | 인사 담당자 | 승인 전에는 노션 쓰기 차단 |
| 3-3 요청·일정 | 승인 후 업무 시스템(노션·캘린더) 등록 (mock) | 인사 담당자. 받는 사람은 처리하고 완료를 회신 | 같은 실행 차단 장치 |

- 근거: 메일은 모두 인사 담당자가 초안을 만들고 확인한 뒤 보낸다(`06_입사_안내메일.md` 머리말). 요청은 인사 담당자가 보내고 경영지원 담당이 처리한다(`08_첫주_캘린더_요청문구.md` 3-2, `01_노션DB_구조.md` 2절).
- 확인 질문: Q12(3-1 리더 확인 범위), Q13(3-3 승인자)

## 5. 데이터팩에서 확인한 문제와 반영
| 문제 (근거) | 반영 |
|---|---|
| 챗 개인 메시지로 한 요청과 회신은 다른 사람이 확인할 수 없다(`05_가상입사자_흐름_채다온.md` 9절, ON-03 · ON-38) | 요청은 노션 DB 행과 메일 스레드로만 만든다. 회신도 같은 스레드에서 받도록 문구에 적는다 |
| 총무 절차 변경이 인사 담당자에게 늦게 전해졌다(`04_온보딩_체크리스트_변경기록.md` 사례 1) | 계정·장비 요청 문구에 「바뀐 절차가 있는지」 질문을 넣는다(v3.1) |
| 첫날 팀 권한을 누가 줄지 몰라 빠졌다(ON-24, 체크리스트 예시 3절) | D-3 팀 권한 요청에서 초대 담당을 미리 정한다 |
| 리더 항목이 자주 늦었다(ON-04 · 09 · 13 늦게 완료) | 리더 체크리스트에 기준일을 보여 준다. 리마인드 여부는 Q16 |
| 입사자는 계정을 받기 전까지 캘린더 초대를 볼 수 없다(`08_첫주_캘린더_요청문구.md` 1절) | 첫날 일정은 메일 3으로 알리고, 캘린더 초대는 계정 생성 뒤로 둔다 |

## 6. 인수 조건 초안
- 입사자 정보 한 건과 양식 v3.2로 메일 6통과 챗 1건 초안을 만들고, 각 초안에 체크리스트 ID가 붙는다.
- 초안에 연락처, 주소, 비밀번호, 처우 값이 없다.
- 담당별 체크리스트 항목 수가 리더 11, 총무 6, 버디 1이다. 조건 항목은 입사자 정보에 맞게 들어가거나 빠진다.
- 승인 전에는 노션·캘린더·Gmail 더미 호출이 모두 차단된다. 승인 뒤 내용이 바뀌면(해시 불일치) 더미 발송도 차단된다.
- 테스트는 데이터팩 원문이 아니라 검토된 가상 fixture로 한다.
